# FirstDev — Roadmap for the remaining work (Parts 4–7)

## Context

The backend is complete through Part 3: auth, CV-Parser, Repo-Analyzer, the Job-Matcher, postings, applications and Assessment-Gen. There are 689 tests, and real end-to-end runs pass for all three parts.

This roadmap covers everything left to reach the goal the user chose.

| Decision | Choice |
|---|---|
| Near-term goal | **Portfolio / demo**: show it working; no email or legal flows; seeded demo data |
| Frontend | **Next.js + TypeScript + Tailwind** |
| Hosting | **GCP Cloud Run** (API, worker, frontend containers) + **Cloud SQL Postgres**, ~$15–25/month |
| Social | **Connections + public profiles**; no feed or messaging |

Each part gets its own spec → plan → Sonnet implementation → Opus review cycle, like Parts 1–3. The order matters: each part depends on the one before it.

## The main risk for a public demo: cost

Anyone who finds the demo URL could sign up and spend the Anthropic budget. Every part designs around this:

- **Invite-code signup:** `FIRSTDEV_INVITE_CODE`. Without the code, visitors can only use the seeded demo accounts.
- **Demo accounts:** read-mostly, with **pre-computed** data, so exploring costs nothing.
- **Global daily LLM budget:** `FIRSTDEV_LLM_DAILY_TOKEN_BUDGET`, counted from logged token usage. When it is exceeded, new LLM jobs are refused with 503 "demo budget reached for today".
- **Outside caps:** an Anthropic workspace spend limit and a GCP billing budget alert. The user sets both in their consoles.

## Part 4 — Backend for the web app and demo safety

| Item | Design sketch |
|---|---|
| Browser sessions | API sets **httpOnly, Secure, SameSite=Lax cookies**: a 15-min access JWT plus a rotating refresh token. The refresh token is stored hashed, revocable, and reuse revokes the whole session family. The existing Bearer header stays for scripts and tests. CSRF: state-changing requests need an `X-CSRF-Token` header matching a non-httpOnly cookie (double submit) |
| CORS | allow only `FIRSTDEV_FRONTEND_ORIGIN`, with credentials |
| Security headers | HSTS, X-Content-Type-Options, frame-ancestors none, Referrer-Policy on the API |
| Demo safety | invite code, global daily token budget, a per-user "demo" flag that blocks LLM-spending routes on seeded accounts |
| LLM fake mode | `FIRSTDEV_LLM_MODE=fake` serves deterministic canned responses, so the frontend's end-to-end tests run for free. It is refused at startup when `FIRSTDEV_ENV=prod` |
| Connections | request, accept, decline, remove, list; rate limit 50/day; no self or duplicate requests (DB constraints already exist) |
| Public profiles | new `handle` (unique, `^[a-z0-9-]{3,30}$`) and `public_profile` flag (default false). `GET /u/{handle}` returns headline, tier, verified badges, repo highlights and connection count, through an allowlist output model. No CV text, contacts or scores |
| Hebrew tech aliases | `ALIASES` gains common Hebrew spellings (פייתון→python, ריאקט→react, ג׳אווהסקריפט→javascript, …) |
| Seed script | `scripts/seed_demo.py` creates demo developer and recruiter accounts with realistic parsed CVs, repo analyses, postings, scores and a graded assessment from fixture JSON. No LLM calls; it is idempotent |

## Part 5 — Frontend (Next.js)

- **Stack:** Next.js (App Router) + TypeScript + Tailwind.
  - Colour, font and effect tokens come from `docs/design-system.md` (dark-first; `#0B0F19`, `#111827`, cyan `#00F2FE`, amber `#FFB703`, `#F8FAFC`; Inter/Geist + JetBrains Mono; glass cards, city-grid background, `< / >` motifs).
  - Typed API client generated from FastAPI's OpenAPI (`openapi-typescript`).
  - **English + Hebrew (RTL)** via `next-intl`, using logical CSS properties throughout.
- **Brand:** an SVG "FD" monogram merged with a skyline built from code brackets; favicon and social preview image.
- **Screens:**
  - **Landing:** what FirstDev is, plus "try the demo" buttons.
  - **Sign-in / invite signup.**
  - **Developer:**
    - profile, CV upload, repos and analysis, badges
    - recommended jobs, match detail with feedback
    - applications, invitations
    - assessments: taking UI with a server-synced timer, and the report
  - **Recruiter:** postings CRUD, applicants with scores, ranked candidate cards, send assessment, assessment results.
  - **Public profile and connections.**
- **Quality:**
  - Playwright end-to-end tests against the backend in fake-LLM mode
  - axe accessibility checks
  - Lighthouse ≥ 90
  - unit tests for components with logic, such as the timer and the score breakdown
- **Security:**
  - strict CSP and no `dangerouslySetInnerHTML`; all user and LLM text is rendered as text
  - injection flags are shown as badges, never rendered as content
  - cookies only, with no tokens in localStorage
- **Prerequisite:** Node.js LTS is not installed. It goes into `~/.local` with no sudo, with the user's OK at Part 5 start.

## Part 6 — GCP deployment

- **Postgres switch:**
  - Run the Alembic migrations on Postgres.
  - CI runs the whole test suite against a Postgres service container as well as SQLite.
  - Job claiming moves to `FOR UPDATE SKIP LOCKED`, so multiple workers are safe.
  - The rate limiters move to a Postgres table, shared across instances.
  - Vectors stay BLOB + numpy (fine for the demo); pgvector is noted as a later upgrade.
- **Containers (Artifact Registry):**
  - **API** (Cloud Run service, scales to zero)
  - **Worker** (Cloud Run with min-instances 1 and CPU always allocated; exposes `/health`). The embedding model is baked into the image.
  - **Frontend** (Cloud Run service)
- **Data and secrets:**
  - Cloud SQL Postgres (smallest tier) through the Cloud SQL connector.
  - Secrets (Anthropic key, GitHub token, JWT secret, invite code) live in **Secret Manager**, never in images or env files.
- **CI/CD (GitHub Actions):**
  - `check.sh`, Postgres tests, frontend tests, image builds, then deploy.
  - GCP authentication uses **Workload Identity Federation**, so there are no long-lived service-account keys.
  - The `/security-review` skill can run on pull requests once the repo has a GitHub remote.
- **Operations:**
  - Cloud Logging (the logs are already PII-free)
  - uptime check
  - billing budget alert
  - automated Cloud SQL backups
- **User actions:** create the GitHub repo (private) and the GCP project with billing. Optionally buy a custom domain (Cloud Run maps it with managed TLS).
